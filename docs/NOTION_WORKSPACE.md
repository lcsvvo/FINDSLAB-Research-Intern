# Notion Workspace 운영 가이드

> 현재 Notion Workspace를 **어떻게 운영할지** 정의하는 공식 규칙 문서다.
> 새 구조를 제안하지 않는다. 현재 구조를 기준으로 운영 규칙만 정의한다.
> 이 규칙은 이후 다른 연구 프로젝트에도 그대로 재사용한다.
>
> **이 문서가 Workspace의 공식 기준(Source of Truth)이다.** 운영 규칙·역할이 바뀔 때는 **먼저 이 문서를 수정한 뒤 Notion을 변경한다.** 문서와 Notion이 다르면 이 문서가 기준이다.

## 1. 목적

### Notion의 목적
- Notion은 **프로젝트 관리·협업·기록**을 담당한다.
- 진행 상황·결정·일정·회의·자료 현황을 한곳에 남겨 **교수님 공유**, **팀 협업**, **연구 종료 후 기록 보존**을 가능하게 한다.
- **이 Workspace는 연구실 공유 공간이다.** 모든 페이지는 작성자가 아니라 **교수님·공동연구자가 읽고 이해**할 수 있도록 쓴다. 판단 기준은 "GitHub와 겹치는가"가 아니라 "**보는 사람이 이해하기에 설명이 충분한가**"이다.

### GitHub와 역할 분리 (엄수)
- **GitHub = 코드·분석·데이터.** 노트북(`notebooks/`), 라이브러리(`src/`), 산출물(`results/`), 원자료(`data/`, git 추적 제외).
- **Notion = 관리·협업·기록.** 진행·결정·회의·일정·자료 메타데이터.
- 판단 기준: **"실행하면 결과가 바뀌는 것"은 GitHub, "누가·언제·왜를 남기는 것"은 Notion.**
- **원본**(전체 코드·전체 표·대용량 데이터·이미지 파일)은 GitHub에 둔다. Notion에는 원본을 그대로 옮기는 대신, 보는 사람이 GitHub를 열지 않아도 이해하도록 **목적·방법·핵심 결과·해석을 충분히 풀어 쓴다.** 겹침 자체가 아니라 **설명 부족**이 문제다.

## 2. 전체 구조

Workspace 루트는 **연구 관리 홈** 페이지이며, 그 아래 문서·DB가 연결된다. 교수님께는 이 홈 링크만 공유한다.
각 DB는 아래 4항목으로 정의한다: **목적 / 사용 시점 / 기록 대상 / 금지 대상.**

### 2.0 연구 관리 홈 (페이지)
- 목적: 전체 진입점. 목적·사용법·모든 DB 링크를 모은 랜딩.
- 사용 시점: 교수님·신규 팀원에게 워크스페이스를 안내할 때.
- 기록: 워크스페이스 사용법과 링크.
- 금지: 개별 연구 내용·진행 기록(각 DB가 담당).

### 2.1 연구 주제 (문서 페이지)
- 목적: 연구의 **핵심 설계**를 한 장으로 소개(배경·가설·방법·데이터·기대 결과).
- 사용 시점: 처음 보는 사람이 5분 안에 연구를 이해해야 할 때. 설계가 확정·변경될 때 갱신.
- 기록: 확정된 연구 설계의 **최종 상태**.
- 금지: 진행 현황·역할 분담·일정·회의·수정 과정 등 관리성/메타 내용.
- 참고: DB가 아니라 단일 문서다. 프로젝트가 하나이므로 문서로 유지한다.

### 2.2 진행 보고 (DB · "격주 진행 보고")
- 목적: **교수님께 2주마다 공유하는 진행 보고.** Workspace 최우선 산출물.
- 사용 시점: 2주 사이클마다 1회차씩 작성.
- 기록: 회차·기간·담당자·상태·핵심 요약. 본문에 `이번 2주 완료 / 다음 2주 계획 / 이슈·질문 / 데이터·결과 링크`.
- 금지: 확정 결정의 상세 근거(→의사결정 기록), 원자료(→데이터 카탈로그), 분석 결과 원본(→GitHub, 링크만).
- 속성: 회차(제목)·기간·담당자·상태(작성 중/공유 완료)·핵심 요약.

### 2.3 회의록 (DB)
- 목적: 회의와 **비정기 소통·피드백** 기록(미팅·이메일·카톡·외부 조언).
- 사용 시점: 회의 직후, 또는 교수님·외부 피드백을 받은 즉시.
- 기록: 회의명·날짜·유형·참석자·핵심 피드백·반영 여부. 본문에 의제·메모·우리 반영.
- 금지: 확정된 결정 자체(회의록은 "무슨 논의·피드백이 있었나"까지, 확정은 →의사결정 기록).
- 속성: 유형(미팅/이메일/카카오톡/외부 조언/기타)·반영 여부(확인 필요/반영함/보류).
- 참석자는 항상 가나다순으로 정렬한다(기존 회의록도 동일하게 적용).

### 2.4 데이터 카탈로그 (DB)
- 목적: **각자 수집한 원자료의 현황**(누가·어디서·처리 상태)을 관리.
- 사용 시점: 새 데이터 수집 시 1행, 전처리·병합 진행 시 상태 갱신.
- 기록: 데이터명·수집자·출처·유형·기간·상태·파일. 부가 설명은 본문에 작성한다.
- 금지: 분석 코드·분석 결과(→GitHub), 읽는 외부 문헌(→참고문헌·자료).
- 원칙: Notion에는 **데이터 자체가 아니라 메타데이터(출처·수집자·상태·저장 위치)**를 관리한다. 실제 데이터 파일과 처리는 GitHub `data/`에 두고, 카탈로그에는 저장 위치·링크만 남긴다.

### 2.5 의사결정 기록 (DB)
- 목적: 되돌리기 어려운 결정과 **그 근거·대안**을 남겨 나중에도 추적.
- 사용 시점: 분석 방법·데이터 처리·모델·범위가 바뀌는 결정을 내렸을 때.
- 기록: 결정·날짜·유형·상태·세부 설명. 배경·근거/대안·기각 이유는 **표에선 키워드**, 상세는 **본문**. 근거가 된 회의는 `근거 회의`로 연결.
- 금지: 아직 논의 중인 사안(→회의록). `확정`·`재검토 필요` 상태만 다룬다.
- 제목(`결정`): 하나의 의사결정을 대표하는 **짧은 명사형**으로 쓴다. 내용을 나열하지 않는다. 예: 토큰화 방식 선정 · 변수 정의 · 회귀모형 선택 · 전처리 전략 · 데이터 제외 기준.
- `세부 설명`: 제목을 보완하는 **1문장**, **명사형으로 끝맺는다**. 상세 설명은 쓰지 않는다(→본문).
- `배경·근거`·`대안·기각 이유`: **핵심 키워드·짧은 명사형만** 쓴다. 상세 설명은 쓰지 않는다(→본문).
- 본문 서식은 **회의록과 동일**하게 `-` 기호와 **제목2(Heading 2)** 소제목을 써서 가독성을 높인다. 소제목은 굵은 텍스트가 아니라 **제목2 블록**으로 만든다. 예:
  ```
  ## 배경·근거
  - ...

  ## 대안 기각
  - ...
  ```

### 2.6 분석 코드 (DB)
- 목적: Notebook의 **진행 상태와 데이터 흐름**을 관리한다. 어떤 Notebook이 어떤 원자료를 사용해 어떤 산출물을 생성하는지 추적한다.
- 사용 시점: 새 Notebook(STEP)을 작성·완료했을 때 1행 등록 또는 상태 갱신.
- 기록: **속성(상단)은 키워드·관계만**, 실제 작업 흐름 순서로 배치한다 — 식별 정보(Notebook) → 작업 정보(담당자·상태) → 실행 정보(사용 원자료→데이터 카탈로그, 생성 산출물→연구 산출물) → 파일 정보(Notebook 파일·연계 소스코드). `파일`류 속성은 맨 앞에 두지 않는다.
- 속성 추가(2026-07-16): **가설**(선택형: Baseline/H1/H2/H3/공통) — Notebook 번호는 분석 수행 순서일 뿐 가설 번호와 무관하므로(예: `04_rate_beta_estimation`이 Baseline), 이 속성으로 가설별 진행 상황을 필터·그룹핑한다.
- 금지: Notebook 코드 내용을 그대로 옮겨 적지 않는다(원본은 GitHub). 산출물 자체의 상세 설명은 연구 산출물(DB)에 기록한다. 설명(목적·내용)은 속성에 두지 않고 본문에 작성한다.
- 관계: 데이터 카탈로그(사용 원자료) · 연구 산출물(생성 산출물)과 연결.
- 원칙: Notebook을 열지 않아도 **목적·입력 데이터·생성 산출물**을 이해할 수 있도록 작성한다. 옮기지 않는 것은 '원본 코드'이지 '설명'이 아니다.

#### 2.6.1 본문 형식 — Notebook 행

모든 Notebook 행은 아래 **제목2 여섯 개**를 같은 순서로 쓴다. 행마다 구성이 다르면 비교가 안 된다.

```
## 목적          연구 질문과 이 STEP이 답하는 것. 관련 가설 명시.
## 입력 데이터   입력 파일·이전 STEP 결과·원자료
## 방법          모형·추정식·표준오차·검정 절차 (구현 파일 경로 병기)
## 생성 산출물   Table/Figure/Variable/Summary를 종류와 개수로
## 핵심 결과     숫자를 포함한 발견 3~5개
## 상태          완료 범위, 출력 위치, 알려진 한계
```

- 해당 없는 절은 비우지 말고 "해당 없음"이라고 쓴다. 절 자체를 빼지 않는다.
- 수치는 GitHub Summary와 일치해야 한다. 다르면 GitHub이 기준이다.

#### 2.6.2 본문 형식 — 공통 설정·라이브러리 행

`config.py`, `src/*.py`처럼 **분석 하나가 아니라 여러 분석이 공유하는 코드**는 위 여섯 절이 맞지 않는다(입력 데이터도 생성 산출물도 없다). 아래 **네 개**를 쓴다.

```
## 목적          이 파일이 무엇을 책임지는가
## 담고 있는 것   파라미터·함수를 항목별로. 값과 근거를 한 줄씩
## 사용 방법      노트북에서 어떻게 불러 쓰는가
## 적용 범위      어느 노트북에 적용됐고 어디는 아직인가
```

- **변경 이력을 날짜별로 쌓지 않는다.** 날짜 문단이 누적되면 지금 값이 무엇인지 알 수 없게 된다. 본문은 **항상 현재 상태만** 적는다. 이력은 GitHub 커밋이 원본이다.
- 값이 바뀌면 해당 항목을 고쳐 쓴다. 옛 값은 남기지 않는다.
- 값 자체의 상세 근거는 코드 주석과 `docs/`가 원본이다. 여기에는 결론과 한 줄 근거만 둔다.

### 2.7 연구 산출물 (DB)
- 목적: `notebooks/`·`src/` 실행으로 생성된 **결과물**(Summary·Figure·Table·Dataset·Variable)의 현황을 관리해 진행 보고·보고서 작성 시 바로 참조한다.
- 사용 시점: 분석 코드(STEP)가 완료되어 새 결과물이 생성되었을 때 등록.
- 기록: **속성(상단)은 키워드·관계만** — 산출물명·유형(Summary/Figure/Table/Dataset/Variable)·담당자·생성 코드(→분석 코드)·관련 회의록·파일. 산출물의 목적·내용·핵심 결과는 페이지 본문에 작성한다.
- 속성 추가(2026-07-16): **가설**(선택형: Baseline/H1/H2/H3/공통) — `results/{Hn}_{설명}/` 폴더 구조와 대응시켜, GitHub 폴더명만 보지 않아도 Notion에서 가설별 산출물 현황을 볼 수 있게 한다.
- 금지: 원본 코드·원자료를 옮기지 않는다. 원자료는 →데이터 카탈로그, 사람이 작성하는 문서(계획서·발표·보고서)는 →문서 허브. 결과물 파일 첨부 규칙은 2.7.2 참고.
- 관계: 분석 코드(생성 코드) · 회의록과 연결.
- 원칙: 모든 산출물은 **생성 Notebook과 연결**한다(생성 코드 relation). 데이터 카탈로그 → 분석 코드 → 연구 산출물의 흐름을 유지하며, 각 페이지는 **무엇을 생성했고 결과가 무엇인지** 이해할 수 있도록 작성한다.

#### 2.7.1 정렬 규칙

기본 보기는 **2단 정렬**을 쓴다.

```
1순위  STEP (숫자, 오름차순)   분석 수행 순서
2순위  유형 (오름차순)         Summary → Figure → Table → Dataset → Variable
```

- **왜 STEP 속성이 따로 필요한가** — 산출물명만으로 정렬하면 같은 STEP 안에서 이름 가나다순이 되어(예: Figures → Summary → Tables) 유형 순서를 지정할 수 없다. STEP을 별도 숫자 속성으로 빼야 2단 정렬이 가능하다.
- **왜 Summary가 먼저인가** — 결과를 처음 보는 사람은 요약부터 읽는다. Figure·Table은 그 근거이고, Dataset·Variable은 재현에 필요한 재료다. 읽는 순서와 정렬 순서를 맞춘다.
- `유형` 선택지의 **정의 순서 자체를** `Summary · Figure · Table · Dataset · Variable`로 유지한다. Notion은 선택형을 이 순서로 정렬하므로, 선택지 순서를 바꾸면 보기 정렬도 함께 바뀐다.
- `STEP` 값은 산출물명 앞의 두 자리 번호와 같게 넣는다(`04 산업별 금리 베타 결과표` → `4`). 여러 STEP이 함께 만든 산출물은 **처음 생성한 STEP** 번호를 쓴다.

#### 2.7.2 파일 첨부 규칙

**첨부 파일은 열람 편의용 사본이다. 원본은 언제나 GitHub이다.**

교수님·공동연구자가 GitHub을 열지 않고도 결과를 확인할 수 있어야 하므로, 결과물은 `파일` 속성에 사본을 붙인다. 다만 Notion을 원본으로 삼지는 않는다.

| | 대상 |
|---|---|
| **첨부한다** | Summary(HTML·MD), Figure(PNG), 결과표(CSV). 개수가 많으면 zip 하나로 묶는다 |
| **첨부하지 않는다** | 원자료, 가공 전 대용량 데이터, 소스코드(`.py`·`.ipynb` 원본) |

- 파일이 갱신되면 Notion 사본도 다시 올린다. **수치가 다르면 GitHub이 기준이다.**
- 사본을 붙였더라도 페이지 본문의 설명을 생략하지 않는다. 첨부는 설명을 대신하지 못한다.
- `data/`·`docs/private/`처럼 git 추적에서 제외한 파일은 Notion에도 올리지 않는다.

## 3. 데이터 흐름

### 데이터 흐름
```
외부 데이터 (KRX · ECOS · DART · 금투협)
   │  수집
   ▼
데이터 카탈로그 (Notion: 메타데이터·상태)
   │  실제 파일은 GitHub data/
   ▼
GitHub 분석 (notebooks/ · src/)
   │
   ▼
Notebook 결과 → results/ (표·그림)
   │
   ▼
Summary (results/ *.md)
   │  링크·요약만
   ▼
진행 보고 (Notion · 2주 단위)
   │
   ▼
교수님 공유 (연구 관리 홈 링크)
```

### 연구 의사결정 흐름
```
교수님 피드백
   ▼
회의록 (논의·피드백 기록)
   ▼
의사결정 기록 (확정 + 근거)
   ▼
GitHub 분석 (방법 반영)
   ▼
Summary (results/ *.md)
   ▼
진행 보고 → 교수님 공유
```

병렬 기록: 외부 문헌 → 참고문헌·자료 / 산출 문서 → 문서 허브.

## 4. 운영 원칙 (규칙)

- **문서 우선**: 운영 규칙·역할 변경은 이 문서를 먼저 수정한 뒤 Notion에 반영한다. 이 문서를 Source of Truth로 삼는다.
- 새 DB를 만들기 전에 **기존 DB로 가능한지 먼저 검토**한다.
- 역할이 겹치는 페이지·DB를 만들지 않는다. **한 정보 = 한 자리.**
- **Source of Truth 원칙**: 하나의 정보는 하나의 DB·문서만 **원본**으로 관리한다. 같은 내용을 여러 DB에 중복 기록하지 않으며, 원본이 아닌 위치에서는 **링크 또는 요약만** 둔다.
- 회의·피드백 결과는 **회의록**에 기록한다.
- 확정된 결정은 **의사결정 기록**에 기록한다. (회의록은 논의까지, 결정은 의사결정 기록)
- 교수님께 공유할 내용은 **진행 보고**에 기록한다.
- 원자료는 **데이터 카탈로그**에서 관리한다. 실제 파일 처리는 GitHub `data/`.
- 최종 산출 문서는 **문서 허브**에서 관리한다.
- 외부 자료는 **참고문헌·자료**에서 관리한다.
- **연구 주제 문서에는 관리성 내용(진행·역할·일정·회의·수정 과정)을 넣지 않는다.**
- GitHub는 코드·분석·데이터를, Notion은 관리·협업·기록을 담당한다. 한쪽 정보를 다른 쪽에 복사하지 않고 **링크·요약으로 연결**한다.

## 5. 운영 규칙 (업데이트 시점)

### 2주 사이클
```
사이클 시작 → 진행 보고 새 회차 생성(기간·담당자)
   ↓ (사이클 중 수시)
회의·피드백        → 회의록 기록 → 반영 여부 갱신
방법·데이터 결정   → 의사결정 기록(확정/재검토) + 근거 회의 연결
데이터 수집·전처리 → 데이터 카탈로그 상태 갱신
분석              → GitHub, 결과 Summary 링크를 진행 보고에 축적
   ↓ 사이클 끝
진행 보고 마감(상태: 공유 완료) → 교수님께 홈 링크 공유
```

### 이벤트별
- 회의/피드백 직후 → 회의록 1행. 실행할 게 있으면 반영 여부 `확인 필요`.
- 되돌리기 어려운 결정 → 의사결정 기록 1행. `근거 회의` 연결.
- 데이터 수집 → 데이터 카탈로그 1행(`수집완료`), 처리 진행 시 상태 갱신.
- 문헌 발견 → 참고문헌·자료 1행.
- 산출 문서 완성 → 문서 허브 1행.
- Notebook 작성·완료 → 분석 코드 1행 등록 또는 상태 갱신.
- 결과물(Summary·Figure·Table·Dataset·변수) 생성 → 연구 산출물 1행.

## 6. 장기 운영 원칙

- **새 프로젝트가 추가돼도 구조를 바꾸지 않는다.** 아래로 확장한다.
  - 연구 주제 문서를 프로젝트별로 1장씩 추가한다(수가 늘면 상위에 목록 페이지).
  - 진행 보고·회의록·의사결정·데이터 카탈로그·문서 허브·참고문헌·분석 코드·연구 산출물은 **프로젝트 구분 속성/태그**로 나눠 같은 DB에 계속 쌓는다. 구분 속성은 다중 프로젝트가 실제로 생길 때만 추가한다.
- DB를 늘리지 말고 **행을 늘린다.** 기록이 쌓일수록 가치가 커지도록 한 곳에 축적한다.
- 명명·형식 규칙은 GitHub `docs/STYLE_GUIDE.md`를 따른다. Notion은 그 산출물을 **링크·요약**으로만 참조한다.
- 연구 종료 시 진행 보고·의사결정·데이터 카탈로그가 그대로 **연구 이력**이 된다. 삭제하지 않고 상태만 종료로 둔다.
